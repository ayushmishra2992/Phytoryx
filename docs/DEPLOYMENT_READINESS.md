## 1. Real-browser verification
Microsoft Edge (Chromium 157, headless) driven by Playwright ran the complete `/v2` workflow: 42/42 checks passed against a CPU-only backend (script outside the repo; results `browser_results.json`). Covered: upload and preview; place + collection time + scale; phyllotaxy, morphology (px and cm, reliability warnings), modelled air quality with validation note and provider-computed indices, measured section "Input required" without an OpenAQ key; downloads of PDF, JSON and HTML from the browser buttons; opening the PDF and HTML; identical values in dashboard, PDF and HTML; 390 px and 768 px layouts (no horizontal overflow); errors (non-image, >10 MB, invalid scale, backend unreachable, PDF endpoint unreachable); edges (unknown place, date without time, no location); GPS denied, and GPS **simulated** (Playwright geolocation override — a real GPS fix was not tested). Not covered: Safari/Firefox/mobile devices, real touch input, screen readers.

## 4. Model weights and Git LFS
Two files, 343 MB each (654.7 MiB; 686 MB LFS upload). **verified:** GitHub Free allows 10 GiB LFS storage and 10 GiB bandwidth per month; downloads/pulls/forks count against the *repository owner's* bandwidth; if the budget is $0 and the quota is exhausted, LFS is blocked for the rest of the month. At 0.65 GiB per full pull, about 15 full clones/pulls (including CI builds) per month exhaust the free quota; verification clones already used some. Release assets are not covered by that page (**not verified** whether they count). Recommendation: do not build from a fresh LFS pull on every deploy; ship weights once (baked into an image, or a release asset / model hub) and cache them.

A 4 GB target leaves ample headroom (a 2 GB limit looks feasible but is untested). **Real container** (Docker Engine 29.1.3, `--cpus=2 --memory=4g --read-only`; `docs/DOCKER.md`): image 1.17 GB compressed / 3.74 GB unpacked; healthy in 18 s; peak cgroup memory 1.59 GB (including reclaimable page cache; anonymous memory ≈ 0.4 GB, true footprint ≈ 1.1–1.2 GB); `/v2/analyze` median 1.18 s on 2 CPUs; PDF 0.15 s; no disk writes. Startup ≈ 18–26 s (models loading). Latency on this 12-thread CPU: `/predict` ≈ 0.33 s, `/v2/analyze` (no external calls) ≈ 0.64 s, PDF ≈ 0.08 s (63 KB); a 2-vCPU host will be slower (not measured). With a location each analysis adds two outbound calls (geocoding + modelled air quality; a third to OpenAQ if a key is set) — typically a few seconds, dominated by the network. Plan for **≥ 4 GB RAM** (2 GB is below the committed memory) and ≥ 2 vCPU. Uploads are processed in memory and not written to disk; the PDF is generated on the CPU in a fraction of a second, so no persistent storage is needed.

## 7. Recommended architecture
1. **Frontend:** the Next.js app (statically prerendered pages) on Vercel Hobby or any static host; build with `NEXT_PUBLIC_API_URL=https://<backend>`; Vercel's Hobby terms regarding non-commercial use should be checked on its Fair Use Guidelines before launch.
2. **Backend:** one container (the repo `Dockerfile`, CPU torch, `api.v2_app:app`) with ≥ 4 GB RAM and ≥ 2 vCPU, always-on or scale-to-zero (~18 s cold start plus model load). For a demo, run it on a project/university machine behind HTTPS. The Dockerfile was built and smoke-tested on 2026-11-14 (see `docs/DOCKER.md`); it has not been tried on any hosting provider.
3. **Weights:** bake into the image at build time from one LFS pull, or fetch once from a hub/release; avoid repeated LFS pulls (10 GiB/month cap).
4. **Uploads / PDF:** in-memory processing and server-side `fpdf2`; no storage. Add an upload size limit at the proxy (the app already enforces 15 MB).
5. **API communication:** HTTPS end-to-end (an HTTPS frontend cannot call an HTTP backend); set `PHYLLO_CORS_ORIGINS` to the exact frontend origin; keep `OPENAQ_API_KEY` only in the backend's secret store.
6. **Before going public:** the API has **no authentication**. A minimal in-app rate limit now protects the expensive `/v2` routes (`/v2/analyze`, `/v2/report/pdf`, `/v2/geocode`, `/v2/ftir/analyse`): 30 requests per 60 s per client IP by default (`PHYLLO_RATE_LIMIT`, `PHYLLO_RATE_WINDOW_S`; `0` disables; `X-Forwarded-For` is trusted only if `PHYLLO_TRUST_PROXY=1`). It is in-memory and per process, resets on restart, shares one budget across users behind the same NAT, and does **not** cover the v1 `/predict` and `/aqi/compute` routes (which `api.v2_app` inherits unchanged), so also rate-limit at the reverse proxy; all users share the server's Open-Meteo quota (10,000/day ≈ at most ~3,000 analyses/day with two calls each) and one OpenAQ key (60/minute); keep the free-tier non-commercial conditions (no ads, subscriptions or paid features) and the visible attributions; confirm academic eligibility with Open-Meteo.
